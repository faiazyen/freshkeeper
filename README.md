# FreshKeeper

An IoT prototype that watches perishable food on a fridge shelf and warns you
before it goes off, built for a bachelor thesis at the Czech University of Life
Sciences Prague.

The system reads a camera, two metal-oxide gas sensors, a load cell and a
temperature/humidity sensor every thirty minutes, classifies each item as
fresh, marginal or spoiled, and surfaces the result in a web interface served
from the device itself. No image leaves the local network.

## What is real and what is simulated

This matters more than anything else in this README, so it goes first.

| Component | Status |
|---|---|
| Image corpus and fresh/rotten labels | **Real.** 12,335 photographs, CC-BY-4.0 |
| Visual CNN training and evaluation | **Real.** Measured on a held-out, leakage-controlled split |
| Software stack: API, database, alerts, interface | **Real.** Runs, tested, 119 tests |
| Physical spoilage model | **Real model, calibrated** against published shelf lives |
| Gas / temperature / humidity / mass readings | **Simulated** from that model |
| Raspberry Pi driver code | **Written, not validated** against instruments |
| Three-state fusion accuracy | Measured **under the simulation**, not on a real shelf |

No public dataset pairs photographs of spoiling food with synchronised sensor
readings, and building one needs a rig running for months. The sensor channel
is therefore generated by a physical model, and every result that depends on it
is reported as a property of that model rather than of the real world.
Validating against instrumented hardware is the first item of future work.

## Results

Held-out test split, group-aware to prevent near-duplicate leakage.

| Model | Accuracy | Macro F1 | Recall (spoiled) |
|---|---|---|---|
| Visual CNN, binary fresh/rotten | 0.980 | 0.980 | 0.980 |
| Vision only, three states | 0.618 | 0.546 | 0.957 |
| Sensor only, three states | **0.969** | **0.969** | **0.983** |
| Fusion, raw concatenation | 0.943 | 0.944 | 0.953 |
| Fusion, projected embedding | 0.960 | 0.961 | 0.957 |

Two findings worth stating plainly, because neither is what the design
predicted:

**Fusion does not beat the sensor branch alone.** Under this simulation the
sensor features and the ground-truth label both derive from the same physical
model, so the sensor branch has privileged access to the target and vision can
only add noise. On real hardware, where sensors are noisier and less complete,
the balance would differ — but that is a hypothesis, not a result.

**Naive late fusion was worse than either fix.** Concatenating a 1280-wide
visual embedding with a 32-wide sensor embedding gives the image branch forty
times the width and it dominates the first fusion layer. Projecting the visual
embedding to 64 first recovered 1.7 points of accuracy.

The binary CNN scores 98% because the public corpus's fresh/rotten distinction
is visually stark — rotten fruit is brown and collapsed. That is exactly why it
does not demonstrate early spoilage detection: the hard case, an item going off
that does not look it yet, is absent from the data.

## Quick start

Needs Python 3.12. TensorFlow does not work on the Python 3.9 that ships with
macOS.

```bash
make venv install
make demo          # seed a database with an accelerated 12-day simulation
make serve         # http://127.0.0.1:5055
```

To reproduce the whole pipeline from the raw download (about 40 minutes,
most of it fine-tuning):

```bash
make all
```

`make help` lists the individual stages.

## The dataset audit

The first training run scored 99.7% on validation, which is not a believable
number. There were no byte-identical duplicates — all 12,335 files hash
differently — but the corpus is an augmented set, and variants derived from the
same original photograph were being split across train and test. In feature
space, 27% of test images sat within cosine 0.95 of a training image.

`scripts/audit_dataset.py` embeds the corpus, joins near-duplicate pairs above
that threshold, collapses connected components with union-find, and splits by
group instead of by image. Residual leakage afterwards: 0.00%.

The retrained model still scored 99.5%, so leakage was not the cause. The task
is simply easy. Finding that out took an afternoon and changed how the results
are framed.

## Performance

End-to-end, per item, measured on the development host:

| Stage | Mean | Share |
|---|---|---|
| JPEG decode and resize | 0.92 ms | 2.1% |
| Preprocess | 0.14 ms | 0.3% |
| MobileNetV2 backbone | 40.83 ms | 92.1% |
| Fusion head | 2.47 ms | 5.6% |
| **Total** | **44.35 ms** | |

The backbone is essentially the entire cost. Scaled by an assumed 7.5x
single-core slowdown, a Raspberry Pi 4 would need roughly 333 ms per item, so
six slots take about 2 seconds of a thirty-minute cycle — 0.1% duty. That is an
estimate from a published ratio, not a measurement on a Pi.

TFLite conversion of the fusion head: 0.575 MB float32, 0.292 MB float16,
0.163 MB int8, with int8 costing 0.4 points of accuracy.
